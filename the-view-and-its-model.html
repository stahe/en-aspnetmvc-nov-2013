    5. The view and its model

    5.1. Introduction

    Let’s return to the architecture of an ASP.NET MVC application:

    In the previous chapter, we examined how ASP.NET MVC presents request information [1] to an action [2a] in the form of a model that may contain validation constraints. This model was passed as input to the action, and we referred to it as the action model. We will now focus on the most common result of an action, the [ViewResult] type, which corresponds to a view V [3] accompanied by its model M [2c]. This model will be called the view model V, not to be confused with the action model we just studied. One is the input to the action, the other is the output.

    Let’s start by creating a new project [Example-03] [1] within the same solution, of the basic ASP.NET MVC type:

    5.3. Using a strongly typed model to pass information to the view

    The previous method has the drawback of not allowing for error detection before execution. Thus, if the view [Action01.cshtml] uses the code

    
<h4>@ViewBag.Info</h4>

    An error will occur because the [Info] property does not exist. The one created by the [Action01] action is named [info]. We can therefore use a strongly typed model to avoid this issue.

    In one of the examples discussed earlier, the action was as follows:

    
    // Action10
    public ContentResult Action10(ActionModel03 model)
    {
      string errors = getErrorMessagesFor(ModelState);
      string text = string.Format("email={0}, day={1}, info1={2}, info2={3}, info3={4}, errors={5}",
        model.Email, model.Day, model.Info1, model.Info2, model.Info3, errors);
      return Content(text, "text/plain", Encoding.UTF8);
}

    The [Action10] action was passing six pieces of information (Email, Day, Info1, Info2, Info3, errors) to its client as a string. We will pass this information to a view model [ViewModel01]. Since this model uses information from [ActionModel03], we will derive it from that class.

    We start by copying [ActionModel03] from the [Example-02] project into the current [Example-03] project:

    and we change its namespace to match that of the [Example-03] project:

    
using System.ComponentModel.DataAnnotations;

{

    [Required(ErrorMessage = "The info2 parameter is required")]
    [MinLength(2, ErrorMessage = "The info2 parameter must be at least 2 characters long")]
    public string Info2 { get; set; }

    [Required(ErrorMessage = "The info3 parameter is required")]
    [MinLength(4, ErrorMessage = "The info3 parameter must be exactly 4 characters long")]
    [MaxLength(4, ErrorMessage = "The info3 parameter must be exactly 4 characters long")]
    public string Info3 { get; set; }
  }
}

    • line 18: In order for the browser to transmit the information entered by a user, we need a form. It is delimited by the <form> tag on lines 18 and 31.

    The HTML <form> tag was introduced in section 2.5.2.1. Let’s review its characteristics:

    form
    
<form method="post" action="FormulairePost.aspx">
    HTML tag
    <form name="..." method="..." action="...">...</form>
    attributes
    name="frmexample": form name - optional
    method="..." : method used by the browser to send the values collected in the form to the web server
    action="..." : URL to which the values collected in the form will be sent.
    A web form is enclosed within the tags <form>...</form>. The form can have a name (name="xx"). This applies to all controls found within a form. The purpose of a form is to collect information entered by the user via the keyboard or mouse and send it to a web server URL. Which one? The one referenced in the action="URL" attribute. If this attribute is missing, the information will be sent to the URL of the document containing the form. A web client can use two different methods, called POST and GET, to send data to a web server.     5.6.6. Handling POST Errors

    We mentioned that if no value was checked or selected for the [CheckBoxesField, SimpleChoiceListField, MultipleChoiceListField] fields, then the corresponding parameters were not part of the posted string, and therefore the model properties with the same names were not initialized.

    Let’s look at the following example:

    • in [1], no checkbox was checked;
    • in [2], the [POST] returns a checked checkbox.

    The explanation is as follows:

    • because no checkboxes are selected, the [CheckBoxesField] parameter is not included in the posted values;
    • the [Action08Post] action proceeds as follows: 
    
    [HttpPost]
    public ViewResult Action08Post(ApplicationModel application, FormCollection posted)
    {
      ViewBag.info = ...
      ViewModel08 model = new ViewModel08(application);
      TryUpdateModel(model, posted);
      return View("Form", model);
}
    • Line 5: The form model is instantiated. However, the constructor used assigns the array ["2"] to the [CheckBoxesField] property;
    • Line 6: The posted values are saved to the model. Since the [CheckBoxesField] parameter is not part of the posted values, the property of the same name is not assigned a value. It therefore retains its value ["2"], which means that when the form is displayed, checkbox #2 is checked when it should not be.

    This issue can be resolved in various ways. We choose to resolve it in the code for the [Action08Post] action:

    
// Action08-POST
    [HttpPost]
    public ViewResult Action08Post(ApplicationModel application, FormCollection posted)
    {
      ViewBag.info = string.Format("Controller={0}, Action={1}", RouteData.Values["controller"], RouteData.Values["action"]);
      ViewModel08 model = new ViewModel08(application);
      TryUpdateModel(model, posted);
      // processing of non-posted values
      if (posted["CheckBoxesField"] == null)
      {
        model.CheckBoxesField = new string[] { };
      }
      if (posted["SimpleChoiceListField"] == null)
      {
        model.SimpleChoiceListField = "";
      }
      if (posted["MultipleChoiceListField"] == null)
      {
        model.MultipleChoiceListField = new string[] { };
      }
      // display form
      return View("Form", model);
    }
    • Lines 9–20: We check whether certain parameters have been submitted or not. If not, we initialize them with the value corresponding to the user not having entered anything. This check was not performed for the drop-down list, which always has an item selected, unlike the other lists.

    5.9.1. Server-side validation

    Consider the following model:

    
using System;
using System.Collections.Generic;
using System.ComponentModel.DataAnnotations;
using System.Net.Mail;

namespace Example_03.Models
{
  public class ViewModel11 : IValidatableObject
  {

    [Required(ErrorMessage = "Required information")]
    [Display(Name = "String of at least four characters")]
    [RegularExpression(@"^.{4,}$", ErrorMessage = "Incorrect information")]
    public string String1 { get; set; }

    [Display(Name = "String of up to four characters")]
    [Required(ErrorMessage = "Required information")]
    [RegularExpression(@"^.{1,4}$", ErrorMessage = "Incorrect information")]
    public string String2 { get; set; }

    [Required(ErrorMessage = "Required information")]
    [Display(Name = "Exactly four characters")]
    [RegularExpression(@"^.{4,4}$", ErrorMessage = "Incorrect information")]
    public string String3 { get; set; }

    [Required(ErrorMessage = "Required information")]
    [Display(Name = "Integer")]
    public int Integer1 { get; set; }

    [Display(Name = "Integer in the range [1,100]")]
    [Required(ErrorMessage = "Required information")]
    [Range(1, 100, ErrorMessage = "Incorrect information")]
    public int Integer2 { get; set; }

    [Display(Name = "Real number")]
    [Required(ErrorMessage = "Required")]
    public double Real1 { get; set; }

    [Display(Name = "Real number in the range [10.2, 11.3]")]
    [Required(ErrorMessage = "Required information")]
    [Range(10.2, 11.3, ErrorMessage = "Incorrect information")]
    public double Reel2 { get; set; }

    [Display(Name = "Email address")]
    [Required(ErrorMessage = "Required information")]
    public string Email1 { get; set; }

    [Display(Name = "Date in dd/mm/yyyy format")]
    [RegularExpression(@"\s*\d{2}/\d{2}/\d{4}\s*", ErrorMessage = "Invalid input")]
    [Required(ErrorMessage = "Required information")]
    public string Regexp1 { get; set; }

    [Display(Name = "Date later than today")]
    [Required(ErrorMessage = "Required information")]
    [DataType(DataType.Date)]
    public DateTime Date1 { get; set; }

    // validation
    public IEnumerable<ValidationResult> Validate(ValidationContext validationContext)
    {
      List<ValidationResult> results = new List<ValidationResult>();
      // Date 1
      if (Date1.Date <= DateTime.Now.Date)
      {
        results.Add(new ValidationResult("Incorrect information", new string[] { "Date1" }));
      }
      // Email1
      try
      {
        new MailAddress(Email1);
      }
      catch
      {
        results.Add(new ValidationResult("Incorrect information", new string[] { "Email1" }));
      }
      // return the list of errors
      return results;
    }
  }
}

    5.9.2. Client-side validation

    All previous validations were performed on the server side. This requires a round trip between the client and the server for the user to see their errors. Client-side validation uses JavaScript code to notify the user of errors as early as possible, and in any case before the POST request.
